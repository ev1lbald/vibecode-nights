# Vibecode Nights — анализ инвестиционного питча

API для тренировки инвестиционного питча. Пользователь выбирает тип инвестора, загружает материалы, отвечает на вопросы и получает оценку проекта и короткий план действий. Этот контракт описывает первую версию для разработчика сайта. Разработка сервера следует отдельным коммитом.

## Что происходит в одной сессии

1. Пользователь выбирает роль критика и отправляет текст питча, один или несколько файлов либо и то и другое. Сервер извлекает текст из `.md`, `.txt`, `.pdf`, `.pptx` и `.docx`. Для PDF нужен текстовый слой. Изображения, сканы и графики без текстовых подписей требуют текстового пояснения в материалах.
2. Критик формирует внутренний пул из 5 общих вопросов и 10 вопросов по каждой из семи категорий. Второй агент получает пул и исходные материалы и выбирает ровно 5 вопросов по значимости для проекта и выбранного инвестора. Критик задаёт пользователю только эти вопросы. Сессия LangGraph приостанавливается до получения ответов.
3. Критик оценивает проект целиком по материалам и ответам. По каждому из десяти критериев возвращается балл и обоснование. Если данных недостаточно, балл равен `null`. Общий балл — среднее выставленных баллов с равными весами. Шкала по умолчанию 0–10.
4. Советчик запускает по одному агенту на категорию. Главный советчик выбирает три действия, которые сильнее всего расширят круг потенциально подходящих инвесторов. Каждое действие должно быть выполнимо за несколько дней, по умолчанию максимум за три. Пользователь получает оценку и советы. Заданные вопросы и советы сохраняются в сессии SQLite.

### Роли критика

| ID | Роль | Приоритеты |
| --- | --- | --- |
| `business_angel` | Бизнес-ангел | Мотивация и вовлечённость команды, потенциал возврата вложений |
| `corporation` | Корпорация | Внутренний заказчик, интеграция, риски для данных и репутации |
| `grant_fund` | Грантовый фонд | Измеримый результат, общественная польза, смета, сроки и отчётность |
| `venture_fund` | Венчурный фонд | Ёмкость рынка, масштабирование, метрики и следующие раунды |

Категории вопросов и советов: рецессия, копирование конкурентом, юридические риски, плохие отзывы, ценовая война, отсутствие клиентов и потеря критической зависимости. [Источник категорий](https://github.com/alexyc9381/crash-test-skill/blob/main/skills/crash-test/SKILL.md#2-seven-crash-dummies-alone)

Критерии оценки проекта: реалистичность решения проблемы, бизнес-модель, анализ рынка и конкурентов, финансовая модель, интеллектуальная собственность или регистрация стартапа, первые продажи, риски, горизонт расчёта, уникальность продукта, инвестиционная привлекательность.

## HTTP API v1

Рекомендуемая схема подключения: браузер обращается к серверу сайта, а сервер сайта — к этому API. Если настроен сервисный токен, сервер сайта передаёт `Authorization: Bearer <token>` во всех запросах к `/api/v1/*` и хранит соответствие UUID сессии пользователю. Передавайте UUID только владельцу сессии. Без сервисного токена API предназначен для локального запуска.

| Метод и путь | Запрос и результат |
| --- | --- |
| `GET /api/v1/config` | Роли `personas` с полями `id` и `label`, категории `categories` и критерии `criteria` с такими же полями, число вопросов `question_count`, число советов `advice_count`, предел срока `max_advice_days`, шкала `score_min` / `score_max`, расширения `file_extensions` и пределы `max_files`, `max_file_bytes`, `max_input_chars`, `max_answer_chars`. |
| `PUT /api/v1/sessions/{session_id}` | Создание сессии. Сайт создаёт UUID и отправляет `multipart/form-data` с обязательным `persona`, необязательным `pitch` и повторяющимся полем `files`. Нужен непустой питч или хотя бы один файл. Запрос возвращает сессию с вопросами. Повтор с тем же UUID и теми же материалами возвращает состояние существующей сессии или продолжает прерванную генерацию. |
| `GET /api/v1/sessions/{session_id}` | Получение последнего сохранённого состояния по UUID, в том числе после перезапуска API. |
| `PUT /api/v1/sessions/{session_id}/answers` | Отправка всех ответов одним JSON-запросом. Тело: `{"answers":[{"question_id":"q-1","answer":"Ответ на вопрос"}]}`. Включите каждый полученный ID ровно один раз и заполните каждый ответ. Повтор той же отправки возвращает готовый результат или продолжает прерванный анализ. |
| `GET /healthz` | Проверка доступности процесса. |
| `GET /docs` | Swagger UI. Схема доступна по `/openapi.json`. |

Оба `PUT` ждут завершения своей стадии. На сайте показывайте ожидание, а при сетевом сбое запрашивайте состояние по UUID. Если стадия осталась незавершённой, повторите соответствующий `PUT` с теми же данными. Одновременная запись в ту же сессию возвращает `409`.

### Объект сессии

| Поле | Формат |
| --- | --- |
| `id`, `persona` | UUID сессии и ID выбранной роли |
| `status` | `generating_questions`, `awaiting_answers`, `analyzing` или `completed` |
| `questions` | Массив `{id, text, category_id}` в порядке показа. Для общих вопросов `category_id` равен `null`. |
| `assessment` | До окончания анализа `null`. Затем `{score, score_min, score_max, criteria}`, где каждый элемент `criteria` содержит `{id, label, score, rationale}`. `score` может быть `null`. |
| `advice` | Массив по убыванию приоритета. Каждый элемент содержит `{category_id, action, expected_result, estimated_days}`. |

При `awaiting_answers` покажите поля по массиву `questions`, сохраняя их ID. При `completed` отобразите общий балл, разбивку по критериям и советы. Используйте фактическую длину массивов. Количество элементов, роли, критерии, шкала и лимиты задаются на сервере.

Ошибки имеют вид `{"detail":{"code":"…","message":"…"}}`. Для валидации полей `detail` также может быть массивом с ошибками OpenAPI. `401` означает проблему с сервисным токеном, `404` — неизвестную сессию, `409` — конфликт состояния или повтор с изменёнными данными, `413` — превышение лимита, `415` — неподдерживаемое расширение, `422` — неполные или нечитаемые данные, `502` — сбой LLM или некорректный ответ после повторных попыток.

## LLM и мониторинг

Сервер использует LangGraph и отправляет запросы в настроенный OpenAI-совместимый `POST /chat/completions`. Модель и базовый адрес настраиваются на сервере. Langfuse фиксирует стадии, длительность, токены при наличии данных от провайдера и ошибки. Передача содержимого промптов и результатов в Langfuse по умолчанию выключена. Тексты материалов и ответов используются настроенным LLM-провайдером и сохраняются в состоянии сессии.
